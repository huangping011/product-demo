# 菜谱实验室 · 8 小时可演示 MVP

基于 PRD 实现的**移动端优先纯前端网页原型**：从「看菜谱 → 按我的条件调整 → 补齐材料 → 做菜 → 交作业 → 回流到复刻区」的完整闭环。

> 所有菜谱、作者、复刻记录、商品与采购入口均为**人工整理的演示数据**，明确标注；不接登录、真实平台授权、支付、订单、实时库存与商家后台。
> 主推用例「山药玉米排骨汤」来自**用户提供的菜谱图片**（原图存于 `public/images/soup-yumi-yao.jpg`），标注「用户提供的菜谱图片」，不绑定未核验的作者与原文链接。

## 一、本地预览

环境要求：Node.js ≥ 20.19（开发验证使用 Node 22.22.2 / npm 10.9.7）。

```bash
cd recipe-lab
npm install
npm run dev
```

打开 <http://127.0.0.1:5173> 即可。建议用浏览器开发者工具切换到 390 × 844 的手机视口；桌面端会自动居中为 460px 手机框。

生产构建与本地预览：

```bash
npm run build     # tsc --noEmit + vite build，产物在 dist/
npm run preview   # http://127.0.0.1:4173
npm test          # 21 项自动化验收测试
```

`dist/` 是纯静态站点（HTML + CSS + JS，无服务端依赖）。`vite.config.ts` 已设置 `base: './'`，因此可直接部署到任意子路径：

- **静态托管**：把 `dist/` 整个目录上传到 Nginx / Apache、腾讯云 COS 静态网站、Vercel、Netlify、GitHub Pages、Cloudflare Pages 等；构建命令 `npm run build`，发布目录 `dist`。
- **本地起服务**：`npx serve dist` 或 `python -m http.server 8080 -d dist`。
- **无需配置**：没有后端路由、没有环境变量、没有 API 密钥、不需要数据库；刷新页面靠 `localStorage` 恢复当前页面与做菜进度。
- 若用 CDN，注意不要缓存 `index.html` 过久；`assets/` 下的文件带内容哈希，可长期缓存。

## 四、AI 接入方式（可选）

默认 **不调用任何模型**：方案由 `src/lib/plan.ts` 的本地规则生成，界面明确标注「非实时 AI 生成」；主推菜提供标注为「预设适配说明」的回退版本，逐条说明锅具/配料替换对风味与口感的可能影响。**人数换算始终由代码完成**，不由模型决定。这让整个流程在没有密钥、没有网络时也能演示。

需要接真实模型时：

1. 自建服务端代理（密钥只放服务端），暴露一个 POST 接口，接收 `{ task:'plan', recipeId, conditions }`，返回 `{ versionName, changes, steps, materials }`。
2. 在项目根目录建 `.env.local`：`VITE_PLAN_API=https://你的服务端/plan`。
3. 前端 `src/lib/ai.ts` 会调用该接口，并用 `validateModelPlan` 校验结构；**只接纳解释性文本**，份量、库存状态、材料缺口、过敏冲突校验、商品关联仍由代码计算。
4. 请求失败或结构不合法时自动降级到本地规则示例方案，并显示明确提示、记录 `model_failure` 事件，不丢失已有条件与资料。

安全约束：模型**不得决定跳转地址**；外部采购链接只从 `src/data/products.ts` 的 `EXTERNAL_TARGETS` 预配置模板生成（材料名仅作为搜索关键词参与 URL 编码）；渠道排序、可用性与站内商品配置同样由该文件决定。前端不存放任何 API 密钥。

## 五、商业化与数据边界

- 商品卡与渠道一律标注「演示」，不展示未经验证的价格、库存、送达时间；若数据里出现 `isAd`，会额外标注「付费推广」。站内确无该品类或没有可用商品配置时显示「本 Demo 暂无站内商品」并给渠道预览，生鲜缺口优先外部即时零售。
- 外部入口为平台搜索页，点击前弹说明「将在外部平台完成购买，以该平台库存、配送和价格为准」；不自动加购、下单、付款，点击后材料仍为「待补齐」。选择替代品后对应必买缺口移除（转入「想还原原版」可选），库存「不确定」单列「先确认」。
- 行为事件记录：清单查看、商品详情点击、外部采购跳转、主动确认已备齐，以及入口点击、方案生成、开始做菜、作业发布等。首页「演示工具 → 行为事件记录」可查看。**MVP 不把点击当作成交**。
- 「发布作业」只写本地演示社区，不宣称发布到真实小红书；「有帮助」只记录反馈，不代表验证安全或有效。
- 依据标签区分 `原作者做法` / `社区复刻参考` / `AI 建议，尚未实测`，不编造成功人数或社区验证。
- 计时结束不代表食物达到安全状态；步骤给出可观察完成状态与风险提示。

## 七、本轮改造与真实笔记核验结论

**关于「接入真实笔记」**：已逐条尝试检索并打开小红书 `explore` 笔记页，站外访问返回不可见 / 404 / 登录墙，**无法核验标题、作者与原文链接是否一致**。按约定不伪造来源：

- 原有 5 道菜谱统一标注「示例」，并在笔记页显示来源说明「示例笔记，未绑定真实小红书链接」；「查看原笔记」打开的是对应的本地演示笔记页（含作者、正文、来源说明），不会跳到未核验的外链。
- 新增主推「山药玉米排骨汤」标注「用户提供的菜谱图片」，图片信息逐字录入（2–3 人份；排骨 350 g、铁棍山药半根、甜玉米 1 根、胡萝卜半根、姜 3 片、盐适量、料酒 1 勺；四步做法），**不绑定作者与原文链接**。若后续确认图片出自某篇公开笔记，再把作者/链接绑定到该用例；同菜的其他真实笔记应作为**单独的「社区参考」**展示，不与图片用例混同。

**四项改造落地位置**：

| 要求 | 实现 |
|---|---|
| 小红书原生 UI | `src/styles.css`（白底、深灰字、细分隔线、小红书红 `#fe2c55` 仅用于主操作与选中态）、`NoteDetail.tsx`（真实大图 + 作者行）、`RecipeCard.tsx` / `DianDian.tsx`（紧凑图文卡）、`Plan.tsx`（结果页信息层级前置） |
| 新增主推菜谱 | `src/data/recipes.ts`（`r6`，`sourceKind: 'user-photo'`，`public/images/soup-yumi-yao.jpg`）、`src/data/community.ts`（2 条示例复刻）、`src/lib/ai.ts`（「排骨怎么做」「想喝清甜一点的汤」命中 `r6`） |
| 条件驱动换算与双版本 | `src/lib/plan.ts`（`scaledNumber` / `quantityText` / `servingsBasisText` / `switchPlanMode`）、`Conditions.tsx`（1–6 人、锅具、三态）、`Plan.tsx`（味道影响 + 「接近原味 / 用现有条件做」） |
| 按缺口匹配渠道 | `src/data/products.ts`（`channelsForGap`、`xhsEntryFor`、`EXTERNAL_TARGETS`）、`ShoppingDrawer.tsx`（必买 / 还原原版可选 / 先确认三组） |

**本地验收结果**（2026-11-12）：`npm test` 21/21 通过，`npm run build` 通过；Chrome 强制 390 × 844 真机视口走完 8 屏（首页 → 主推笔记 → 条件 → 4 人份 → 方案 → 补齐清单 → 点点对话 → 排骨提问），每屏 `scrollWidth === 390`，无横向溢出。核验到：4 人份排骨显示 560 g、盐显示「适量（按口味）」、结果页四段顺序正确（能怎么做 → 味道会怎么变 → 要补什么 → 详细步骤）、双版本可切换、清单出现「必买缺口 / 先确认 / 本 Demo 暂无站内商品」、点点「排骨怎么做」返回山药玉米排骨汤卡片并带「按我的条件做」。

真机验收中同时修正了 4 个细节：条件页「份量基准说明」判断条件写错导致不显示、示意菜谱数量仍写「5 道」、点点输入栏「发送」按钮在 390px 下折成两行、做菜页副标题硬编码「第 3 步 / 共 5 步」。
